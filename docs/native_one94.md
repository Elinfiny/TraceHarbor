# Dormant native ONE94 source candidate

This candidate implements a separately guarded GitHub-hosted writer route. It
does not qualify or activate a native invocation. Its workflow is outside
`.github`, has literal `if: false`, and only describes a manual, single job,
Ubuntu 24.04, attempt-one recipe. No install or secret injection is executed.

## Actual source path

`OneRequest -> load_context94 -> authenticated capture -> _oidc94 -> signed
ordinary claims -> exact run/attempt job membership -> authenticated numeric
grant -> registered context -> execute_native94`. The consumer then calls the
shared exact payload/full evidence validators, `OneBackend -> _NativeGitCore94`
for a create-only consumed record and complete immutable readback, lazily obtains
the model credential under the exposure enforcer, and calls `NativeHTTP94`.
That class reuses the unchanged `nebius.HTTPBoundary.exchange` algorithm. The
unchanged decode, full evidence verifier, dossier builder and record verifier
complete the path; only a small fixed receipt is projected publicly.

The former unconditional native loader refusals in `one_request.py` and
`one_backend91.py` are replaced with guarded loader/consumer and producer
wiring. `_GitRecordCore` factors the existing strict algorithm without changing
the synthetic subclass/namespace. The native path has its own plan, operation,
record classification and `refs/tags/traceharbor-native-one94-consumed/` recipe.
It has no local consume ledger. A serialized receipt or callback is not native
authority. Only the registered, authenticated same-process invocation can enter
the native producer; restart, collision, late/ambiguous reply or changed record
means consumed UNKNOWN, no retry, delete, update, adoption or refund.

`qualification/native27_oidc67.py` contributes only its pure exact request
origin/path/query policy. Its read-only acquisition/native-factory contract is
neither called nor relaxed for this writer. The selected verifier65 PyJWT
`PyJWK.from_dict`/`decode` RS256 signature/issuer/audience method is implemented
in the separate94 caller because verifier65's reviewed expectations remain
unbound and must not be assigned by this candidate. Ordinary `workflow_ref`,
`workflow_sha`, repository IDs, actor, ref, event, run/attempt, times and
`check_run_id` are mandatory. Reusable-only `job_workflow_*` claims are not
invented. Exact run/attempt-one jobs metadata binds `check_run_url` to the
signed check-run identity; a job ID is not assumed to equal a check-run ID.
Pure claim checks in tests are data checks, never a signature attestation.

Git transport uses validated TLS to the exact repository on api.github.com,
fixed 2022-11-28 API version, documented allowlisted GET/create-only POST paths,
bounded complete bodies and JSON media validation. There is no redirect,
retry, implicit pagination, ref update or delete route. Response JSON media is
validated before normalization into the existing backend's JSON representation.
Tokens are obtained lazily, used only in Authorization headers and never put
in public receipts, URLs, claim records or logs. Request payload bytes are not
regenerated: 4836 bytes, SHA256
`a6c905b718e0770f87efc1058f1961beaee6de172c7ab31c74fdbf82774a9b95`;
the complete 598-byte input and full normalized evidence hashes remain exact.
Model/project stay exact Nano / `aiproject-e00d73xwjm884tnvcs`, n=1,
1500 maximum completion tokens, stream=false, store=false, json_object.

One original monotonic window covers acquisition, verification, durable claim,
credential, HTTP, verification and cleanup. Actual grant expiry can only shorten
that window. Socket timeouts are refreshed from its remaining time. Objects and
partial bytes enter private original custody before classification/post-return
checks; primary UNKNOWN stays sticky and cleanup errors are ordered secondary.
Resource assignment occurs inside guarded calls so a late returned connection
is still closed. Timeouts do not promise kernel or billing cancellation.
